<Chapter n="01" title={<>A social app with <em>one job.</em></>}>

Most social apps rank by attention. I wanted one that ranks by shared interest. Follower-based networks push people towards comparing themselves with others, and Meetup charges organisers and does little for one-to-one discovery, with no real-time chat. The research question was whether content-based matching with AI embeddings could give useful recommendations to people who had only just signed up.

I picked Next.js for server rendering, routing and PWA support, and Supabase over Firebase for full SQL, no lock-in and cost. I built a PWA, not a native app, so one codebase reached every phone without app store releases. It's still running: you can [try it live](https://connecthub-nu.vercel.app) or [read the code](https://github.com/ifeanyianyanwu/connecthub).

<Chapter n="02" title={<>Matching on meaning, <em>not just tags.</em></>}>

Exact tags miss near neighbours. Someone into bouldering and someone into climbing share nothing on paper. So each user's hobbies become a Gemini embedding stored on their profile, refreshed whenever the hobbies change. Communities get one too, built from their hobbies, category, name and description, in that order of weight.

Two Postgres functions do the ranking. For people, one blends Jaccard similarity on shared hobbies with the cosine similarity of the embeddings. For communities, the other blends exact hobby overlap with the same embedding similarity. Both use a 60/40 split, and both skip people I'm already connected to and communities I've already joined.

Exact overlap keeps the bigger share because the app can explain it: "you both like X". The embeddings fill in the related interests that use different words.

<Chapter n="03" title={<>The app that kept <em>logging people out.</em></>}>

After the PWA shipped, everything passed in the desktop browser. The bug only showed up when I installed it on my phone: close the app, open it again, and I was back on the login page. Every time.

Desktop testing never closed the app the way a phone does, so it could never have caught this. The proxy that guards each page was checking the session with `getClaims()`, which verifies the token locally and never refreshes it, and the session cookie had the default lifetime. Reopening the app after a while meant an expired token, nothing to refresh it, and a redirect to login.

The fix was one call and one setting. The proxy now uses `getUser()`, which asks Supabase and refreshes the session through the cookie, and the cookie lasts 400 days (same-site, secure in production). After that, the reliability check "sessions persist without re-login" passed.

The service worker needed the same care. Calls to Supabase and to my own API routes always go to the network, because auth and data must never be stale. I also turned off the automatic reload when the phone comes back online, because it would wipe a half-written post.

</Chapter>

<Chapter n="05" title={<>Live, <em>without polling.</em></>}>

Likes, comments, messages and notifications appear for everyone viewing, without a refresh. Five screens subscribe to Supabase Realtime: messages, connections, post cards, the notification panel and the unread badge. Post cards update likes straight away and keep the count live for every viewer.

Notifications started as Postgres triggers that inserted a row. I moved them into the app so one call could do two things: write the in-app notification, then send a Web Push to each of the recipient's devices, clearing out subscriptions that no longer exist. A trigger can't send push on its own.

In testing, messages arrived in under a second and push notifications in under two. One limit I couldn't design around: iOS only delivers Web Push once the app is added to the home screen.

</Chapter>

<Chapter n="06" title={<>It passed its tests. <em>Then I reviewed it.</em></>}>

Every functional requirement had its own test case, run on a preview deployment in Chrome and iOS Safari, and all 24 passed. I also tried cross-user queries from the browser console (blocked by row-level security) and script injection in posts (escaped). Five people worked through set tasks, and all of them finished every task. What tripped them up: no way to withdraw a connection request (two sent one by mistake), an unlabelled filter icon, no upload progress, and vague error messages.

Months after I handed it in, I reviewed the code again and found holes the tests never looked for. The notification actions trusted the IDs the browser sent, so anyone could fake who a notification came from. The email confirmation route would redirect to another site. And an unused accept action let any user accept any connection request.

The lesson: row-level security protected the tables, but server actions are public endpoints too. They have to work out who's calling from the session, never from their arguments. Each action now takes only the ID of the like, comment or connection, checks it belongs to the signed-in user, and works out the recipient on the server. While I was there I brought the README back in line with the code, a habit I wrote about in [Docs must match the code](/journal/docs-must-match-the-code).

</Chapter>

<Chapter n="08" title={<>What I'd do <em>differently.</em></>}>

I'd make the AI matching a stretch goal, not a core deliverable, and get it working on exact overlap first. I'd recruit testers early enough for more than one round, and I'd add automated tests, CI, and versioned SQL and security policies from the start, so the database lived in the repo and not only in Supabase.

Scope discipline mattered too. I built account deletion late in the project, then reverted it the same day because the report had put data export and deletion out of scope. It's first on the list for what comes next, for GDPR. After that: a third signal from collaborative filtering, blocking, and editing posts.

</Chapter>
